# 作者模型能力边界评估

评估对象：`checkpoints/sac/sac_triple_final.pt`
MD5：`31868d591a8671e17564540cfe01f758`（与仓库根目录 `sac_triple_final.pt` 完全一致，无需再拷贝）
评估工具：`tools/eval_policy.py`（不改动 `env.py`，直接用 `set_state` 覆盖初始分布）

HR 任务要求：① 自然下垂/大角度起始 → ② 自主摆起 → ③ 保持直立 ≥ 10 s → ④ 同一个策略完成。

---

## 1. 结论：作者模型是 B（近直立 → 保持平衡），不是 A

**它不会摆起。** 不是"摆得不好"，是根本没有这个行为。

### 判别证据

判别"摆起"和"混沌甩动路过竖直"的标准很简单：看 `tip_y > 1.7` 的**连续**停留时长。
真摆起应该是 tip_y 升上去之后长期停在 1.8 附近；混沌甩动只会瞬间掠过 1.7 然后掉下去。

| 初始分布 | 连续保持 >1.7 的最长时长 | 通过 10 s 的局数 | tip_y>1.7 的步数占比 | 动作饱和率(>0.95) |
|----------|------------------------|----------------|--------------------|------------------|
| `exact`（完全竖直） | 50.00 s | **50/50** | 100.0% | 0.0% |
| `author`（近直立 ±0.1） | 中位 50.00 s，均值 30.34 s | **30/50** | 60.8% | 8.0% |
| `mixed`（env.py 当前分布） | 中位 0.00 s，最大 50.00 s | 2/50 | 4.4% | 30.0% |
| `large`（±1.2 rad） | 中位 0.00 s，最大 0.50 s | **0/50** | 0.1% | 28.0% |
| `hanging`（自然下垂） | 中位 0.00 s，最大 0.10 s | **0/50** | 0.0% | 32.0% |

关键数字（`hanging`，100 局，关闭提前终止跑满全程）：

```
best tip_y attained : mean=1.494  max=1.796
episodes whose tip EVER crossed 1.5 : 68/100
episodes whose tip EVER crossed 1.7 : 28/100
fraction of steps with tip_y > 1.7  : 0.0%     <-- 决定性
action saturation share             : 36.0%
max |hinge angle|                   : 258.9 rad（杆在自由打转）
```

虽然 68/100 局里 tip 在某个瞬间冲过 1.5，但 **tip_y>1.7 的步数占比是 0.0%**——
那只是混沌甩动时"路过"竖直位置，没有一次停住。同时 36% 的步数动作打满 ±1、
杆累计转了 258 rad，说明策略在这个状态域里是**乱打**，不是在蓄能。

对比：`author` 分布下动作饱和率只有 8%（且主要集中在跌落后的挣扎段），
`exact` 下是 0.0%。策略只在直立邻域内有意义。

### 作者模型的真实工作包线

| reset 噪声 | 表现 |
|-----------|------|
| `0.0`（完全竖直） | 50/50 全程保持，几乎零动作 |
| `0.05`（训练时用的值，≈ ±2.9°） | 20/20 全程保持，tip_y 最低 1.749，小车最多用到 0.965 |
| `0.1`（env 默认值，≈ ±5.7°） | 只有 56/100 局站住，40%+ 在 25 步内跌落 |
| `±1.2 rad`（≈ ±69°） | 完全失效 |

README 的 *Known limitations* 一节作者自己写了这一点：
"The saved policies balance indefinitely at 0.05 and 0.0, but fall within about 25 steps
on roughly three of five seeds at 0.1."

**即：作者模型的舒适工作区只有 ±0.05 rad（±3°），连自己 env 的默认 ±0.1 都守不住。**

## 2. 为什么"作者模型 + fine-tune"走不通

你已经试了 5 次（错误 3/4/5 都是这个思路），失败不是调参问题，是结构性的：

1. **没有先验可继承。** 从下垂状态看，作者策略的动作是乱打（36% 饱和）。
   它对"如何蓄能"没有任何表示，fine-tune 等于让一个只会局部平衡的网络
   从零学一个全局任务，起点并不比随机初始化好。

2. **梯度方向冲突。** 大角度 reset 的梯度会把网络在直立附近的精准行为改掉。
   这正是你观察到的"继续训练破坏了原来的平衡能力"
   （错误 5：step=100 时 tip_y 从 1.777 掉到 1.116）。

3. **任务本身是复合的。** "摆起 + 保持"对三级倒立摆来说，能量塑形是必需的，
   而 GitHub 这个仓库的 reward 只有存活 + 距离 + 速度惩罚三项，
   没有任何鼓励蓄能的项。从下垂起步时这个 reward 的梯度几乎为零
   （离目标太远，`distance_penalty` 的梯度方向不指向"先获得动能"）。

## 3. 面向 HR 任务的可行路线

前提修正：任务要求"同一个策略完成摆起+稳定+扰动恢复"，
所以**必须改 env 的 reset 与终止逻辑**，这不是可选项——当前
`termination_height=1.5` 会让任何下垂起始在第 1 步就判负。

### 推荐路线：能量塑形 + 角度课程 + 条件终止

| 改动 | 内容 | 作用 |
|------|------|------|
| 终止条件 | 改为**条件终止**：只有当本局曾达到过 `tip_y > 1.7` 之后再跌破 1.5 才判负 | 保留"跌倒"信号，同时允许从下垂起步 |
| reward | 加能量塑形项：`+ k · (E_target − \|E − E_target\|)`，E 为相对悬挂最低点的总能量，`E_target` 为直立能量 | 给出明确的蓄能梯度，这是 swing-up 的标准做法 |
| reset 课程 | ±0.3 → ±0.6 → ±1.2 → π，按成功率自动晋级 | 避免一步到位 |
| 训练量 | 从零训，SAC，500 万–1000 万步起步 | 作者 PPO 脚本默认就是 1000 万步，说明作者也知道这个量级 |

课程每级晋级判据建议直接用本工具的指标：`episodes passing 10 s >= 80%`。

### 若时间紧的降级方案

把摆起物理难度降下来，这是合法的建模自由度（HR 要求的是"三级串联倒立摆"，
没有规定杆长质量分布）：

- **顶部杆更短更轻**（如 0.6/0.6/0.3 m），swing-up 所需能量大幅下降；
- **导轨加长**：当前 ±1 m 是硬约束，从 −1.8 m 举到 +1.8 m 需要 +209 J，
  500 N × 2 m 行程 = 1000 J/扫摆，理论可行但耦合效率低。改 XML 一行到 ±2 m，
  swing-up 难度显著下降。

这两个改动都只动 `assets/inverted_triple_pendulum.xml`，不动算法。

## 4. 复现方式

```bash
python tools/eval_policy.py --checkpoint sac_triple_final.pt --all-starts --episodes 50
python tools/eval_policy.py --checkpoint sac_triple_final.pt --start hanging --episodes 100
python tools/eval_policy.py --checkpoint sac_triple_final.pt --start author --episodes 100 --terminate
```

`--start` 可选 `author / hanging / large / mixed / exact`；
`--terminate` 打开后按原始任务口径（`tip_y<=1.5` 判负）；
不加则跑满 1000 步，用于测摆起能力。

报告里的 "LONGEST CONTINUOUS hold above 1.7" 直接对应 HR 的"保持稳定直立不少于 10 秒"
（10 s / 0.05 s = 200 个连续控制步）。

### 关于 `python evaluation/viz.py`

它现在用 `termination_height=-999`，所以 GUI 里：
- 初始状态由 `env.py` 当前的课程 reset 决定——**60% 的概率你会看到一个已经倒下/下垂的摆**；
- 作者模型在这些状态下只会乱甩，50 秒后自动 reset 换一个初始状态；
- 只有约 30% 的概率落在近直立分支，那时才能看到它正常平衡。

所以 GUI 里"看起来不行"不代表模型坏，是初始分布不对。要看作者模型的正常表现，
用上面的 `--start author` 跑数值，或者临时把 `env.py` 的 `reset_model` 换回原来的
±0.1 分布再看 GUI。
